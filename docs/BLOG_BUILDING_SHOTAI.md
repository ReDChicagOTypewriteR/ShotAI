# 我为什么做 ShotAI：把本地模型变成真正能用的内网工作台

![ShotAI 本地 AI 工作台](images/shotai-product-preview.png)

很多本地 AI 项目从“模型已经跑起来了”开始，也在这里结束。

第一次在 Ollama 里看到模型正常输出时，确实会有一种事情已经完成的感觉。但当我试着把它交给其他人使用，问题才真正出现：他们不知道什么是端口，不关心模型格式，也不应该为了问一个问题去学习命令行、跨域配置、显存占用和推理参数。

这也是我做 ShotAI 的起点。

我想解决的从来不只是“如何在本地运行一个模型”，而是另一个更具体的问题：

> 当模型已经运行在一台电脑上，怎样让一个团队里的普通使用者真正用上它？

## 跑起来和能使用，是两件不同的事

Ollama 已经很好地解决了模型下载、加载和推理。但从推理服务到一个可以交付的产品，中间仍然隔着很多细小而真实的问题。

浏览器怎样连接本地服务？其他电脑怎样访问主机？图片应该怎样提交给视觉模型？PDF 和 DOCX 如何解析？知识库没有 Embedding 模型时是否还能工作？一个几 GB 的 GGUF 文件如果不完整，应该在什么时候告诉用户？Windows 电脑关闭窗口之后，内网服务是否还应该继续运行？

这些问题单独看都不大，但它们叠在一起，就决定了一个项目到底是“开发者演示”，还是“普通人可以使用的工具”。

ShotAI 逐渐变成了模型运行时之上的一层产品。Ollama 负责计算，ShotAI 负责连接使用者、文件、浏览器和局域网。

这种分工也是我在开发中一直坚持的取舍：不重写已经成熟的推理引擎，把精力放在使用模型这件事本身。

## 为什么选择本地和局域网

把所有能力放到云端当然更容易统一管理，但并不是每一种资料都适合离开自己的设备或单位网络。

很多团队真正关心的并不是参数规模，而是几个朴素的问题：

- 我输入的内容会去哪里？
- 文件是否会上传到外部服务器？
- 断网之后还能不能继续使用？
- 能不能只让内部电脑访问？
- 模型和数据是否由自己控制？

ShotAI 当前没有接入第三方 AI API。对话、设置、知识库索引和最近生成记录主要保存在浏览器本地，推理请求通过 ShotAI 主机转发给回环地址上的 Ollama 或图片服务。

我也不想把“本地”包装成一个绝对安全的词。内网客户端提交的提示词和文件仍然需要经过局域网发送到主机；当前版本也还没有登录、HTTPS、审计和细分权限。因此它适合可信、受控的内网，而不是直接暴露在公网。

明确边界比制造安全感更重要。

## 从聊天框开始，但没有停在聊天框

ShotAI 最初的核心仍然是对话。

现在的工作台支持流式回答、停止、继续、重新生成，以及编辑原问题后重答。会话可以搜索、重命名、删除和导出，回答参数也能按对话保存。

这些功能看起来很常见，但在本地模型场景里，它们背后意味着更多状态需要被正确处理：请求如何中止、重新回答时从哪条消息开始、视觉图片怎样随上下文继续传递、长回答和长输入如何保持可操作。

我慢慢意识到，AI 产品中的很多体验并不来自模型，而来自模型之外那些不显眼的状态管理。

## 图片、文档和知识库

真实工作中，问题通常不会只以一段文字出现。

所以 ShotAI 加入了图片理解，以及 TXT、Markdown、PDF、DOCX 文档解析。文档先在浏览器中处理，再作为上下文交给本地模型。扫描 PDF 暂时没有 OCR，旧 DOC 也需要先转换为 DOCX。这些限制都应该被直接告诉使用者，而不是用一个模糊的“文件解析失败”带过。

知识库则采用了一种可以降级的设计。

有 Embedding 模型时，ShotAI 使用向量检索；Embedding 不可用或查询失败时，仍然会回退到关键词和中文匹配。回答会展示来源文件、段落和摘录，让使用者知道哪些资料片段进入了上下文。

我不希望知识库因为缺少一个额外模型就完全不可用。能力可以降低，但基础路径不能轻易断掉。

## 模型导入不是一个上传按钮

本地模型经常很大。一个错误如果发生在上传数 GB 之后，付出的不只是等待时间，还有使用者对工具的信任。

因此 ShotAI 对 GGUF 导入增加了更早的检查：读取版本、张量数量和模型说明，计算文件摘要，判断视觉主模型和 mmproj 是否配对，并在模型创建后执行最小推理验证。

这些检查不会让模型格式变简单，但能把错误变得更早、更具体。

我越来越相信，一个本地 AI 工具是否可靠，不只看它成功时能做什么，也要看它失败时能否告诉用户发生了什么。

## 把图片创作放回对话

图片生成最早可以被做成一个独立页面，但实际使用时，文字对话、图片理解和图片修改常常是连续发生的。

现在 ShotAI 把本地图片创作放进聊天输入区域。使用者可以直接描述图片，也可以添加一张参考图，调整改动幅度，再由本地 stable-diffusion.cpp 运行组件完成生成或修改。

生成过程支持进度、停止、预览和 PNG 下载，参考图与结果也会保留在当前对话中。内网电脑不需要单独安装图片运行环境，仍然通过主机完成任务。

这里的重点不只是“支持图生图”，而是让它和原来的对话流程保持一致。功能越多，界面越不应该让使用者频繁切换思考方式。

## Windows 交付比网页开发更接近现实

ShotAI 的另一个重要方向，是让它能够在 Windows 主机上被真正安装和启动。

项目经历过原生轻量启动器，也加入了 Electron 桌面客户端。现在 Electron 主进程可以直接提供 9090 工作台、转发 Ollama 与图片服务，并通过托盘管理窗口和服务生命周期。

关闭主窗口后，内网服务可以继续运行；需要时从托盘重新打开，也可以彻底退出。日志、端口占用、管理员权限和运行组件位置，都需要被纳入交付流程。

这部分开发让我对“打包”有了新的理解。打包不是把源码压缩成一个文件，而是决定目标电脑缺少什么、保留什么、失败时去哪里看原因，以及卸载时哪些数据不应该被删除。

模型权重没有放进安装包，也是一个有意的选择。模型文件巨大，授权和硬件需求各不相同，把它们与应用强绑定会让交付更重，也更难解释。

## 个人开发中最难的是保持边界

独立开发很容易产生一种冲动：只要想到的功能都应该立刻加入。

但 ShotAI 越往后做，我越需要提醒自己，它当前是什么，以及它还不是什么。

它已经能够完成本地对话、视觉理解、文档问答、知识检索、模型管理、图片生成、参考图修改和内网访问；但它还没有账号体系、跨浏览器数据同步、图片任务队列、扫描 PDF OCR、HTTPS 和审计日志。

把未完成的功能诚实地写下来，并不会让项目显得不完整。相反，这能帮助我判断下一步是否仍然服务于最初的问题。

对我来说，开发 ShotAI 的过程也是一次产品边界的练习：不是不断增加功能，而是让每一项功能能够被理解、被验证，并在失败时保持可控。

## 我希望 ShotAI 接下来成为怎样的工具

未来我更关心的不是再增加多少入口，而是把已经存在的能力变得更稳。

例如，主机首次启动时能否统一检查 GPU、端口、磁盘、运行时和模型；多人同时生成图片时能否排队并限制资源；敏感内网能否获得登录、HTTPS、访问控制和审计；会话与知识库是否可以在授权范围内共享；推理层是否可以在保持现有交互的前提下接入更多本地运行时。

这些都不是当前已经完成的功能，而是 ShotAI 继续成为一件可交付工具时，需要逐步解决的问题。

## 写在最后

我做 ShotAI，不是为了证明本地模型可以运行。

这件事早已被很多优秀的推理项目证明了。

我更想做的是，把“模型能运行”继续向前推进一步：让不熟悉模型、不熟悉命令行、也不想研究部署细节的人，依然可以在自己的电脑和局域网里使用 AI。

如果 ShotAI 最终能够让使用者少理解一点底层配置，多专注一点自己的资料和问题，那么这个项目就实现了它最初的目的。
