# ShotAI 产品边界与一体化路线

## 当前实际架构

```text
内网浏览器
    │
    ▼
ShotAI 主机服务
  - 网页与静态资源
  - /ollama 同源代理
  - 健康检查
    │
    ▼
Ollama 推理运行时
    │
    ▼
本地文本 / 视觉 / Embedding 模型
```

ShotAI 已经负责工作台、流式对话、附件解析、图片传输、知识库检索、会话
持久化、模型识别、内网访问和诊断；Ollama 负责模型加载、GPU 调度、上下文
缓存和推理。

因此它不是“只有一个聊天页面”，但当前也没有取代 Ollama。更准确的定位是：
**ShotAI 是产品层，Ollama 是可替换的推理引擎层。**

## 为什么还会感觉是 Ollama 套壳

如果部署时仍要求管理员手动安装 Ollama、执行命令下载模型、分别启动两个
程序，用户感受到的确实还是“给 Ollama 加了网页”。这不是 Java 或 Vue
造成的，而是安装、运行和模型生命周期尚未被一个发行包统一管理。

目前 Windows 内网包已经去掉了客户端 Node.js 依赖，并支持从
`vendor/ollama/windows` 携带 Ollama 运行文件；但仓库不会自动包含 Ollama
二进制和模型，所以没有放入这些文件时，主机仍需预装 Ollama。

## 推荐的产品路线

不建议现在重写推理引擎。优先把 Ollama 作为内部运行时隐藏在 ShotAI 后面，
做成“一体化设备式部署”：

1. 安装包内置经过验证的 Ollama 版本，由 ShotAI 启动器统一启动和关闭。
2. 提供离线模型包格式，清单中包含语言 GGUF、`mmproj`、校验值、能力和推荐
   参数。
3. 首次启动完成 GPU、端口、磁盘、模型完整性和视觉能力自检。
4. 模型中心负责安装、卸载、切换、预热和资源占用提示，不要求用户执行命令。
5. ShotAI 后端使用统一的 `InferenceProvider` 接口，未来可以接入
   llama.cpp、vLLM 或其他运行时，而不改前端。
6. 最后再制作 Windows 安装器和系统服务，实现开机启动、日志收集和升级。

达到以上状态后，终端用户只会看到 ShotAI，不需要理解 Ollama；Ollama 只是
随产品交付的内部组件，类似浏览器内核之于桌面应用。

## 如果完全移除 Ollama

可以把 llama.cpp 直接嵌入原生后端，但需要自行承担模型格式兼容、CUDA
构建、GPU 分层、流式协议、视觉编码器、模型并发、缓存和跨平台发布。这会
显著增加维护成本。只有当需要深度定制调度、授权或运行时体积时，才值得进入
这一阶段。
